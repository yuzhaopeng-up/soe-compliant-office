## 异常检测算法

### 阈值优先级

1. 若 `threshold_config` 中对某 metric 配置了 `upper`/`lower`，直接使用
2. 若未配置，使用 2σ 规则：超过 mean ± 2*std 为异常
3. 若 std = 0（所有值相同），无异常

### 异常判断流程

```
对于 metric M 的每个数据点 d:
  1. 若 d > upper_threshold → 异常 HIGH
  2. 若 d < lower_threshold → 异常 LOW
  3. 若 |d - mean| > 2 * std → 异常 OUTLIER
  4. 否则 → 正常
```

### 异常输出格式

```json
{
  "item": "XX部门-业务异常",
  "field": "业务量",
  "value": 287,
  "expected": 152,
  "deviation": "+88.8%",
  "reason": "超过2倍标准差(阈值152), 自定义upper=200, 实际287"
}
```

### 特殊情况

- 数据量 < 5：不执行异常检测，输出警告
- 所有值相同：std=0，无异常
- threshold_config.upper < threshold_config.lower：忽略配置，回退 2σ

## 趋势判断算法

### 前提条件

- time_field 必须存在且有效
- 时间序列至少 3 个数据点

### 判断规则

| 条件 | 判定 |
|------|------|
| 连续3期变化率 > 0 | 持续上升 |
| 连续3期变化率 < 0 | 持续下降 |
| 变化率标准差 > 均值 × 0.5 | 剧烈波动 |
| 变化率绝对值均 < 5% | 基本持平 |
| 其他 | 小幅波动 |

### 变化率计算

```
change_rate[i] = (value[i] - value[i-1]) / value[i-1] × 100%
```

### 趋势输出格式

```json
{
  "field": "业务量",
  "direction": "持续上升",
  "change_rate": 12.5,
  "from": 120,
  "to": 165,
  "period": "2026-06-01 ~ 2026-06-15"
}
```

## 维度拆解规则

### 分组计算

对每个 dimension 的每个值：
1. 计算该组每个 metric 的 SUM 和 COUNT
2. 计算该组占总量的百分比

### TOP 识别

- TOP3：按 metric SUM 降序取前 3
- 输出组名、汇总值、占比

### BOTTOM 识别

- BOTTOM1：按 metric SUM 升序取第 1
- 输出组名、汇总值、标注"拖累项"

### 多维度交叉

若 dimensions 包含多个字段，先按第一个维度分组，在每个组内按第二个维度再分组。

## 洞察生成规则

### 三段式结构（强制）

每条 insight 必须包含：

1. **what（发生了什么）**：具体数据点陈述
   - 正确示例："XX部门6月业务异常达287件，占全集团18.9%"
   - 错误示例："XX部门业务量较多"

2. **why_matters（为什么值得关注）**：与基准的偏离
   - 正确示例："超过均值88.8%，突破自定义阈值200"
   - 错误示例："需要关注"

3. **suggestion（建议怎么做）**：可执行行动
   - 正确示例："建议XX部门运维团队排查6月业务异常集中区域，优先处理XX下属单位"
   - 错误示例："加强管理"

### 洞察数量

- summary 模式：0 条
- trend 模式：1-2 条
- anomaly 模式：每条异常 1 条
- comparison 模式：2-3 条
- insight 模式：3-6 条（数据量充足时）

### 禁止模式

- 禁止无数据的定性判断
- 禁止无法执行的建议
- 禁止"需要进一步分析"作为唯一建议
- 数据不足时禁止编造结论

## 置信度计算

```
confidence = min(1.0, base_score × data_quality × completeness)

base_score:
  - 数据量 >= 30: 1.0
  - 数据量 10-29: 0.7
  - 数据量 < 10: 0.3

data_quality:
  - 空值率 < 5%: 1.0
  - 空值率 5-20%: 0.8
  - 空值率 20-50%: 0.5
  - 空值率 > 50%: 0.2

completeness:
  - metrics 全部存在: 1.0
  - metrics 缺失 1 个: 0.7
  - metrics 缺失 > 1 个: 0.4
```

## 洞察质量红线

1. **数据映射红线**：每条洞察必须引用至少 1 个具体数值
2. **异常归因红线**：每条异常必须说明判断依据（是阈值还是统计偏离）
3. **建议可执行红线**：建议必须包含具体动作，不能只有方向
4. **数据不足红线**：当 confidence < 0.3 时，insights 最多 1 条，且必须标注"数据不足以支撑深入结论"
5. **脱敏红线**：洞察中不得出现客户姓名、手机号、证件号、详细地址
