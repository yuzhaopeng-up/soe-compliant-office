## 第5章 通信协议与协同规范

"没有规矩，不成方圆。集群的协同效率，取决于通信协议的严谨程度。"

### 5.1 任务描述的标准格式

一个好的任务描述，应该包含四个要素：

#### 要素一：背景

- 为什么要做这个任务？
- 当前的状态是什么？
- 相关的上下文信息

#### 要素二：目标

- 任务的具体目标是什么？
- 成功的标准是什么？
- 期望的输出格式

#### 要素三：约束

- 时间限制
- 资源限制
- 质量要求
- 合规要求

#### 要素四：输出要求

- 输出格式（Markdown/JSON/表格）
- 详细程度（摘要/详细）
- 特殊要求（卡片式/分段发送）

这些要素不是空谈规范，而是从实战中提炼的最低信息量。有一次，Hermes给KimiClaw下达了一个模糊任务："查一下某企业的风险情况"。KimiClaw返回了一份3000字的全面风险报告，涵盖司法风险、经营风险、财务风险、市场风险、信用风险五大类——但Hermes只需要知道"是否有重大诉讼"这一条。信息过载导致Hermes浪费了15000 Token解析这份报告，而且关键的诉讼信息淹没在冗长的分析中，差点被遗漏。从那以后，任务描述必须包含明确的目标和输出要求，"查一下"这种模糊表述被禁止。

另一个案例来自贷前尽调场景。ArkClaw收到一个分析任务但没有"约束"字段，于是它对所有财务指标做了杜邦分析——包括5年趋势、同业排名、行业预测——最终输出了12000 Token的报告。而实际需求是"快速信用评估，只需要3个核心指标"。缺少约束信息，导致Token浪费了约4倍。在日Token限额900万的约束下，这种浪费是不可接受的。

### 5.2 消息协议规范

#### 消息结构

所有节点间通信遵循统一的JSON消息格式：

```json
{
  "message_id": "msg_20260606_001",
  "timestamp": "2026-06-06T14:30:00Z",
  "from": "调度节点",
  "to": "节点A",
  "type": "task_request",
  "priority": "P1",
  "payload": {
    "task": "分析某科技企业财务数据",
    "context": "对公尽调",
    "deadline": "2026-06-06T15:00:00Z"
  }
}
```

#### 消息类型

| 类型 | 用途 | 示例 |
| --- | --- | --- |
| task_request | 任务请求 | "请分析某企业" |
| task_response | 任务响应 | "分析完成，结果如下..." |
| progress_update | 进度更新 | "数据采集中...30%" |
| error_report | 错误报告 | "API超时，正在重试" |
| heartbeat | 心跳检测 | 节点在线状态 |

协议设计中有几个工程细节值得说明。

message_id采用"msg_YYYYMMDD_NNN"格式，其中NNN是当日序号。这个格式保证了全局唯一性，同时便于按日期检索。有一次排查问题时，需要找到6月3日的第17条消息——直接搜索"msg_20260603_017"即可定位，比UUID更高效。

priority字段取值P0-P3，与日Token限额的优先级对齐。P0是紧急任务（系统故障、安全事件），P1是信号任务（用户触发的实时任务），P2是轮询任务（定时检查），P3是对话任务（日常对话）。优先级不仅影响任务调度顺序，还影响Token分配——P0任务可以从P3的额度中"借"Token。

payload字段是灵活的，不同消息类型的payload结构不同。但有一个硬性约束：payload中不得包含P3级（机密）数据的明文。如果任务涉及机密数据，payload中只放数据引用（如"data_ref": "local://myopenclaw/enterprise_001"），实际数据在本地节点间传递，不经过消息协议。

### 5.3 进度同步机制

#### 实时进度展示

```
正在处理：某科技企业尽调报告
├── [完成] 企业信息采集完成（KimiClaw）
├── [进行中] 财务数据分析中...（ArkClaw）30%
├── [等待中] 风险信号扫描（KimiClaw）
└── [等待中] 行业研究（ArkClaw）
预计完成：2分钟后
```

#### 避免"黑盒"

用户最怕的是"不知道系统在做什么"。进度同步的核心原则是：

- 每个步骤都有状态标识
- 预计完成时间透明
- 异常状态及时通知

进度同步的实现经过了一次重要的优化。v1版本中，每个节点每10秒向Hermes发送一次progress_update，无论是否有进展。这导致大量"噪音消息"——KimiClaw在等待天眼查API响应的30秒内，连续发送了3条"数据采集中...无进展"消息，对Hermes的调度判断毫无帮助，却消耗了消息处理资源。v2版本改为"状态变化时推送"：只有当进度百分比发生变化、或状态从"等待"变为"进行中"时，才发送progress_update。这个改动将进度消息量减少了约70%。

另一个优化是超时预估。最初版本的预计完成时间是根据历史平均耗时计算，但实际波动很大——同一个"企业信息采集"任务，快的时候2秒完成，慢的时候因为API限流，需要90秒。后来改为"基于历史同类型任务的P75耗时"作为预估基准，同时引入"超时预警"：如果实际耗时超过预估的2倍，自动发送一条WARNING级别的告警。这让用户对进度的预期管理更准确，减少了"到底还要等多久"的焦虑。

### 5.4 成果交接规范

#### 输出格式标准化

所有输出遵循"卡片式"规范：

- 关键结论前置
- 数据分段展示
- 支持状态标注
- 手机端友好

卡片式规范的一个具体约定是"三段式结构"：每张卡片必须包含"结论→数据→来源"三段。这个约定来自一次教训：ArkClaw曾经输出过一条风险分析结论"该企业经营风险较高"，但没有附数据和来源。风控经理追问"依据是什么"时，Hermes不得不再次调用ArkClaw补充分析，白白浪费了一轮API调用。自此以后，任何结论都必须紧跟支撑数据和来源引用。

#### 可追溯的引用

每个结论都必须标注来源：

- 数据来源（API名称、时间戳）
- 计算过程（公式、参数）
- 推理依据（规则、模型）

引用追溯的工程实现是：每个输出结果的末尾附加一个"provenance"字段，记录生成这条结果的全链路信息——哪个节点生成的、用了哪个Skill、调用了哪个数据源、基于哪个版本的规则、耗时多少Token。这个字段不展示给最终用户，但在审计时可以一键追溯。due-diligence的115份报告中，每一份都包含完整的provenance信息，满足了合规审计的"可追溯"要求。

### 5.5 冲突解决机制

#### 冲突类型

1. 数据冲突：两个节点返回的数据不一致
2. 结论冲突：两个节点对同一问题的结论相反
3. 资源冲突：多个任务争抢同一资源

#### 解决策略

| 冲突类型 | 解决策略 |
| --- | --- |
| 数据冲突 | 多源验证，以权威来源为准 |
| 结论冲突 | 调度节点仲裁，或标记需人工复核 |
| 资源冲突 | 优先级队列，P0优先 |

#### 冲突场景案例

上述策略看似简单，但实际冲突场景的处理远比表格复杂。以下是三个真实案例。

**案例一：数据冲突——天眼查与巨潮资讯的注册资本不一致**

在一次企业尽调中，KimiClaw同时从天眼查和巨潮资讯网采集某上市公司的注册资本。天眼查返回"5亿元"，巨潮资讯返回"4.5亿元"。两个数据源都是权威来源，以谁为准？

处理过程：Hermes检测到同一字段（注册资本）的两个值不一致，触发数据冲突流程。首先，检查时间戳——天眼查的数据更新时间为2026年5月，巨潮资讯的数据来自2025年年报。其次，查证企业是否在2025-2026年间增资——KimiClaw从工商变更记录中确认该企业2026年3月增资5000万元。最终判定：天眼查数据更新（反映增资后），以天眼查为准；同时在报告中标注"注册资本2026年3月由4.5亿增至5亿"。

关键规则：数据冲突时，时间戳更新的优先；但必须查证差异原因，不能简单"取最新"。

**案例二：结论冲突——信用评估与风险扫描结论矛盾**

ArkClaw基于财务指标给出某企业"信用评级BBB+，建议授信"的结论，同时KimiClaw的风险扫描发现该企业"近6个月新增3条被执行记录，总金额1.2亿元"，标记为"高风险"。

处理过程：Hermes检测到结论冲突后，不自动仲裁——金融领域的结论冲突涉及专业判断，不能由调度节点"投票"决定。而是将两个结论同时展示给用户，标注"结论冲突"，并列出各自的依据。最终由用户（风控经理）决定：参考KimiClaw的风险发现，将信用评级下调至BB，同时提高授信条件（增加担保要求）。

关键规则：结论冲突时，调度节点不自动裁决，标记后交人工判断。自动裁决在金融领域是不可接受的风险——一次错误裁决可能导致数百万的信贷损失。

**案例三：资源冲突——两个P1任务同时争夺KimiClaw**

上午10:15，两个用户同时提交P1任务，都需要KimiClaw做数据采集。KimiClaw的并发能力有限（同时只能处理2个采集任务），出现了排队。

处理过程：Hermes的任务队列按优先级排序，两个P1任务优先级相同。进一步判断：任务A是"紧急舆情监控"（高管被调查），任务B是"日常贷前尽调"。虽然优先级相同，但业务紧急度不同——Hermes根据任务上下文中的"紧急程度"字段，将任务A优先分配给KimiClaw，任务B暂时排队。同时，Hermes将任务B降级为"使用备用数据源"模式，由Hermes直接调用天眼查API完成基础采集（质量降低但可交付），KimiClaw空闲后再补充深度数据。

关键规则：优先级相同且资源冲突时，按业务紧急度降级排序，同时为低优先级任务提供降级方案，而非简单阻塞。

### 5.6 本章小结（基础篇）

1. 任务描述四要素：背景、目标、约束、输出要求。缺失任何一个，都可能导致Token浪费或结果偏离预期。

2. 消息协议：标准化JSON格式，5种消息类型，payload禁止包含P3级数据明文。

3. 进度同步：状态变化时推送（非定时轮询），P75耗时预估，超时2倍自动告警。

4. 成果交接：卡片式输出、三段式结构（结论→数据→来源）、provenance全链路追溯。

5. 冲突解决：数据冲突查原因不简单取最新、结论冲突不自动裁决交人工、资源冲突提供降级方案不阻塞。

### 5.7 集群协作新技能

2026年二季度，龙马集群新增了5个集群协作Skill，每个都通过了完整的测试（5/5或6/6通过），显著提升了节点间的协同能力。

#### 5.7.1 clawlink-interop：ClawLink CLI封装

测试通过率：6/6

clawlink-interop是对ClawLink命令行工具的Python封装，提供6个核心接口：

1. status()——查询本节点及对端节点的连接状态
2. friend_list()——获取好友节点列表及在线状态
3. discover()——发现局域网内的可用节点
4. send_message(target, content)——向指定节点发送消息
5. dispatch_task(target, task)——向指定节点分发任务
6. poll_messages()——轮询本节点的未读消息

这6个接口覆盖了集群通信的基本需求：发现节点、建立连接、发送消息、分发任务、接收反馈。clawlink-interop的底层通过ClawLink的加密通道传输，保证了消息的端到端加密。

工程细节：poll_messages()是一个阻塞式接口，默认超时30秒。如果采用简单轮询，一个节点每30秒调用一次poll_messages()，24小时就是2880次调用。在6个节点的集群中，每天的轮询调用量达到17280次。为了减少无效轮询，我们引入了"长轮询+事件通知"机制：当有新消息时，ClawLink主动推送事件，poll_messages()立即返回；没有消息时，最长阻塞30秒后返回空。实测中，日均轮询调用量从17280次降至约2160次，减少87%。

#### 5.7.2 redis-message-bus：全异步Redis消息总线

测试通过率：引擎就绪，待Redis服务器恢复（当前Redis不可达）

redis-message-bus是一个全异步的消息总线，支持三种通信模式：

1. Pub/Sub模式——广播消息，适用于集群公告、配置变更通知
2. Stream持久化模式——消息持久化存储，适用于任务分发和结果回传，保证消息不丢失
3. 服务发现——节点启动时注册到Redis，其他节点通过服务发现找到可用的对端节点

与ClawLink的点对点通信不同，Redis消息总线支持"一对多"和"多对多"通信。典型场景：Hermes发布一条"配置变更"通知，所有节点通过Pub/Sub同时收到，无需逐一发送。

当前状态：Redis引擎代码和测试用例已通过5/5测试，但由于Redis服务器尚未恢复运行，消息总线暂时不可用。集群当前使用ClawLink和GitHub异步通道作为替代。一旦Redis恢复，消息总线将作为L4层通信基础设施投入运行，大幅提升多节点通信效率。

关键设计决策：为什么同时需要ClawLink和Redis？因为两者定位不同——ClawLink是节点间的加密通道，保证安全性和私密性；Redis是高性能的消息总线，保证吞吐量和可靠性。正常情况下，轻量级消息走ClawLink，大批量数据走Redis Stream。Redis不可达时，全部降级到ClawLink和GitHub异步通道。

#### 5.7.3 feishu-group-bot：飞书群Bot协作

测试通过率：5/5

feishu-group-bot让集群节点能够通过飞书群与用户交互，核心能力：

1. Bot身份映射——4个集群节点（Hermes、ArkClaw、KimiClaw、MyOpenClaw）各自绑定了独立的飞书Bot身份，用户可以在群里@不同的Bot节点下达任务
2. 消息事件解析——解析飞书群消息的事件回调，提取@对象、消息内容、发送者身份
3. 意图识别——根据消息内容判断任务类型（查询、分析、报告、审批），路由到对应的Skill

关键经验：群聊禁止reply tag。这是feishu-group-bot开发过程中踩的一个大坑。飞书群消息支持"引用回复"功能，最初我们在群聊中用reply tag实现"对话线程"——每个任务的消息用reply tag串联，形成完整的对话上下文。但实测发现：飞书群聊的reply tag在不同客户端（桌面端/移动端/网页端）的展示行为不一致，某些客户端无法正确渲染嵌套的reply tag；更严重的是，当消息量较大时，reply tag的嵌套层级过深，导致某些消息被折叠，关键信息不可见。最终方案：放弃reply tag，改为在每条消息中附加task_id前缀。例如"[task_001] 分析完成：某企业信用评级BBB+"。task_id前缀在所有客户端都能正确展示，且支持搜索过滤。

#### 5.7.4 cluster-health-monitor：集群健康监控

测试通过率：6/6

cluster-health-monitor提供三维健康监控：

1. ClawLink连接状态——检测各节点的ClawLink连接是否正常
2. Redis心跳——检测Redis服务是否可用，消息总线是否畅通
3. 节点存活检测——通过心跳机制判断各节点是否在线

监控结果以三种方式输出：实时状态查询（按需调用）、周期性健康报告（每小时生成一次）、告警推送（异常时主动推送）。告警分为3级：INFO（信息通知）、WARNING（需要关注）、CRITICAL（需要立即处理）。

当前集群状态快照：
- ClawLink：正常（ArkClaw在线，其他节点待连接）
- Redis：不可达（消息总线不可用，已降级到GitHub异步通道）
- 其他节点：状态未知（心跳未建立，可能在线但未注册）

这个快照说明集群当前处于"部分可用"状态：核心的ClawLink通道正常，但Redis和大部分节点尚未完全在线。cluster-health-monitor的价值在于让运维人员随时掌握集群的真实状态，而非凭记忆或猜测判断。

#### 5.7.5 github-async-handoff：GitHub异步协作

测试通过率：5/5

当需要实时通信以外的异步协作时，GitHub成为集群的"共享白板"。github-async-handoff提供5个核心接口：

1. create_task(repo, task)——在GitHub仓库创建Issue作为任务卡片
2. claim_task(repo, issue_number)——节点认领任务，将Issue的assignee设为自己
3. complete_task(repo, issue_number, result)——标记任务完成，关闭Issue并附结果摘要
4. push_code(repo, branch, files)——推送代码到指定分支
5. pull_code(repo, branch)——拉取指定分支的最新代码

GitHub异步协作的典型场景是"跨时段协作"。例如，KimiClaw在下午5点完成数据采集，但ArkClaw此时已下线。KimiClaw将采集结果push到GitHub的data-branch，同时在Issue #42中记录"数据采集完成，请ArkClaw明日分析"。第二天ArkClaw上线后，pull最新数据，认领Issue #42，完成分析后close并附结果。整个过程不需要两个节点同时在线。

### 5.8 5层通信架构的工程实现

龙马集群的通信不是单一协议，而是5层架构——每一层有不同的技术栈、不同的安全等级、不同的适用场景。

#### L1：ClawLink加密通道

定位：节点间的实时加密通信层。

技术实现：ClawLink基于WebSocket长连接，所有消息在传输前经过AES-256加密。每对节点之间维护一个独立的WebSocket连接，连接建立时通过节点证书做双向认证。

适用场景：轻量级消息传输——任务指令、状态查询、心跳检测、短文本结果返回。

限制：单条消息大小限制为1MB，不适合传输大文件或大批量数据。当需要传输年报PDF（通常5-20MB）时，需要走其他层。

#### L2：GitHub异步通道

定位：跨时段、跨节点的异步协作层。

技术实现：使用GitHub REST API v3，通过Personal Access Token认证。任务以Issue形式存储，代码以Branch/PR形式管理。所有操作通过github-async-handoff Skill封装。

适用场景：不需要实时响应的协作——数据交接、代码审查、文档共享、跨时段任务认领。

优势：天然具备版本控制和审计日志——每一次Issue的创建、认领、关闭都有时间戳和操作者记录，满足合规审计要求。

限制：受GitHub API rate limit约束（每小时5000次请求），高并发场景下需要做请求合并。此外，所有数据存储在GitHub服务器，不适合传输P3级敏感数据。

#### L3：飞书Bot层

定位：用户交互层，连接集群与业务用户。

技术实现：基于飞书开放平台的Bot SDK，4个节点绑定独立的Bot身份。消息通过飞书服务器中转，支持群聊和私聊两种模式。意图识别通过本地的规则引擎实现，不调用外部模型——减少延迟和Token消耗。

适用场景：用户主动触发的任务——在飞书群中@Bot节点下达指令、查看结果、反馈意见。

关键约束：飞书消息体大小限制为30KB，长报告需要分段发送。此外，飞书服务器中转意味着消息不经过集群内部网络，数据安全等级低于L1和L2——因此飞书层只传输P0/P1级数据，P2级数据需脱敏后传输，P3级数据禁止走飞书通道。

#### L4：飞书多维表格层

定位：结构化数据的共享和可视化层。

技术实现：飞书多维表格作为共享数据库，各节点通过飞书API读写表格数据。每张表格有严格的schema定义，字段类型包括文本、数字、日期、选择项、关联字段。

适用场景：需要多节点共享和人工查看的结构化数据——客户信息表、任务进度表、风险预警表。

典型用例：Hermes将尽调任务的关键信息写入"尽调任务看板"表格，字段包括：企业名称、任务状态、负责节点、预计完成时间、风险等级、关键发现。风控经理在飞书中直接查看这张表格，不需要等Hermes推送报告。同时，ArkClaw完成分析后，将风险等级和关键发现更新到同一张表格，Hermes和其他节点可以实时读取更新——形成了"多写多读"的协同模式。

#### L5：生态资源层

定位：外部数据源和工具的集成层。

技术实现：通过Skill引擎的engine.py封装各类外部API——天眼查、巨潮资讯、裁判文书网、国税总局等。每个外部API有独立的调用频率限制和错误处理策略。

适用场景：外部数据采集和验证——企业工商信息查询、财报数据下载、司法信息检索。

安全约束：所有外部API调用必须经过白名单校验，非白名单的URL不允许调用。API Key存储在MyOpenClaw的本地密钥库中，不写入代码或配置文件。

#### 5层架构的协同工作

5层不是各自为政，而是协同运作。以一个完整的贷前尽调任务为例：

1. 用户在飞书群@Hermes_Bot下达任务（L3层触发）
2. Hermes通过ClawLink向KimiClaw发送数据采集指令（L1层传输）
3. KimiClaw调用天眼查API采集企业信息（L5层获取）
4. KimiClaw将结构化数据写入飞书多维表格（L4层共享）
5. Hermes通过ClawLink告知ArkClaw数据就绪（L1层通知）
6. ArkClaw从飞书多维表格读取数据，完成分析（L4层读取）
7. 如果ArkClaw不在线，KimiClaw将数据push到GitHub（L2层异步）
8. ArkClaw上线后从GitHub拉取数据，完成分析（L2层恢复）
9. ArkClaw将分析结果通过ClawLink返回Hermes（L1层回传）
10. Hermes在飞书群推送最终报告给用户（L3层交付）

10个步骤，4层协同，1层备用。任何一层出问题，都有降级方案：L1不可用→降级到L2；L3不可用→降级到L1直接返回；L4不可用→降级到L2的Issue存储；L5不可用→KimiClaw使用备用API或标记"数据缺失"。
