## 第4章 节点设计与分工

"好的分工，让1+1>4；坏的分工，让1+1<2。"

### 4.1 节点设计的基本原则

在设计龙马集群的六个节点时，我遵循了三个基本原则。这些原则不是理论推导出来的，而是在一次次踩坑中沉淀下来的经验。

#### 原则一：单一职责

每个节点只负责一个专业领域，不跨界。ArkClaw只做长文本分析，不碰代码开发；KimiClaw只做代码和数据，不写报告。

为什么？专业分工带来深度。一个节点如果什么都做，最终什么都做不好。就像医院里的医生，内科医生不去做外科手术——不是不能做，而是不专业。

这个原则来自一个真实的教训。在龙马集群的早期版本中，Hermes节点承担了"调度+报告生成+数据采集"三重角色，结果出现了一个严重问题：Hermes在生成尽调报告时，会将自己的分析结论与数据采集结果混淆——把"预期的财务指标"当作"实际采集到的财务指标"写入报告。一次训练课程的现场演示中，Hermes为一家人工智能企业生成了尽调报告，其中的营收增长率使用了"行业平均15%"而非真实采集的"3.2%"，幸亏客户经理在汇报前做了人工复核。这之后，我把报告生成从Hermes剥离，交给ArkClaw专职处理，Hermes只做调度，再也没有发生过类似问题。

另一个案例来自KimiClaw。在未做职责隔离时，KimiClaw曾经在一项贷前尽调任务中既负责数据库SQL查询，又负责风险分析报告撰写。它写出的风险分析报告出现了"自我引用"：数据来源标注为"KimiClaw数据分析"，实际上数据也是它自己生成的。这种"自产自销"在金融领域是绝对不可接受的——审计要求每条结论都有独立数据源佐证。引入审计要求后，我们把KimiClaw严格限定在数据采集层，报告生成交给ArkClaw，实现了数据生产与数据分析的角色隔离。

#### 原则二：能力互补

节点之间不是竞争关系，而是互补关系。ArkClaw擅长报告但不懂代码，KimiClaw擅长代码但不擅长报告——两者协作，弥补了各自的短板。

为什么？集群的价值在于"协同产生增量"。如果节点之间能力重叠，不仅浪费资源，还可能产生冲突（两个节点给出矛盾结论）。

互补设计的最好证明，是贷前尽调智能体（due-diligence）的产出。这个智能体需要同时完成"数据采集+财务分析+风险扫描+报告撰写"四件事。如果交给任何一个单节点完成，输出质量会急剧下降——KimiClaw能采集数据但写不好杜邦分析，ArkClaw能写报告但做不了数据库查询。设计中，KimiClaw负责企业工商信息、司法信息的API采集和SQL查询，ArkClaw负责年报解读、财务指标计算和风险因素分析，MyOpenClaw负责敏感数据的本地处理。三个节点的输出最终由Hermes汇总，生成一份完整的尽调报告。截至2026年6月，due-diligence智能体已经产出了约115个上市公司的JSON+MD配对报告——每家公司一张JSON结构化数据卡、一份Markdown尽调报告。这个产出量，单一节点在同等质量下是不可能实现的。

互补原则的反面案例也有。在集群迭代过程中，我曾短暂地让ArkClaw和MyOpenClaw都具备"财报分析"能力，因为MyOpenClaw需要分析脱敏后的财报数据。结果在分析同一家企业时，两个节点因使用不同的指标口径（ArkClaw用扣非净利润，MyOpenClaw用归母净利润），给出了截然不同的盈利能力判断。解决方案是：财报解读只由ArkClaw负责，MyOpenClaw只做脱敏处理和本地存储，不做二次分析。能力去重之后，再没有出现过结论冲突。

#### 原则三：容错独立

每个节点可以独立运行，不依赖其他节点。如果ArkClaw离线，KimiClaw仍然可以完成数据采集；如果KimiClaw超时，Hermes可以标记"数据缺失"，用已有信息生成报告。

为什么？金融场景要求高可用。单点故障不能导致整个系统瘫痪。节点的独立性，是集群容错能力的基础。

这个原则的实战检验来自一次意外宕机。2026年5月的一个工作日下午，KimiClaw所在的服务器因内存溢出重启，整个数据采集能力停摆了约40分钟。当时Hermes正在处理一个紧急的舆情监控任务——某银行客户因高管被调查引发负面舆情，需要立刻评估影响。如果整个集群耦合在一起，舆情监控任务会随之停摆。但容错设计让Hermes直接降级调用天眼查API采集企业信息，同时由ArkClaw基于已有的企业基本面数据做初步判断，15分钟内输出了第一版快速评估报告。虽然标注了"数据采集节点离线，部分信息待更新"，但关键的舆情定性和风险等级判断已经到位，客户经理据此做了及时响应。

另一个容错独立性的体现是WorkBuddy的定时任务。WorkBuddy每天凌晨2:00执行日志备份、Token消耗统计、Skill版本同步三项运维任务。这些任务的执行完全不依赖其他任何节点——即使在某个凌晨Hermes和ArkClaw同时停机维护，WorkBuddy照样完成备份，日志不会丢失。这种独立性在金融场景中至关重要：审计要求操作日志不可中断，任何一天的空白都是合规风险。

### 4.3 节点间的协作关系

#### 核心协作链

用户 → Hermes（调度）
  ├→ KimiClaw（数据采集）
  │   └→ 外部API（天眼查、裁判文书网）
  ├→ ArkClaw（分析/报告）
  │   └→ 外部数据（年报、行业报告）
  ├→ MyOpenClaw（隐私/安全）
  │   └→ 本地计算（数据不出域）
  ├→ WorkBuddy（运维/定时）
  │   └→ 定时任务（备份、监控）
  └→ CodeBuddy（代码/测试）
      └→ GitHub（代码仓库）
Hermes ← 各节点返回结果
Hermes → 用户（汇总报告）

#### 典型协作场景

场景一：企业尽调

Hermes拆解任务
  → KimiClaw采集企业信息（并行）
  → ArkClaw分析财务数据（并行）
  → KimiClaw扫描风险信号（并行）
  → ArkClaw行业研究（并行）
Hermes汇总
  → 一致性校验
  → 生成报告
  → 推送用户

场景二：代码开发

用户："开发一个发票查验脚本"
Hermes分配
  → CodeBuddy生成代码
  → KimiClaw架构评审
  → CodeBuddy编写测试
  → WorkBuddy定时执行
Hermes汇总
  → 代码+测试+部署方案

场景三：敏感数据处理

用户："分析这批客户数据"
Hermes识别敏感数据
  → MyOpenClaw本地处理（数据不出域）
  → MyOpenClaw脱敏
  → ArkClaw分析脱敏后数据
Hermes汇总
  → 分析报告（无敏感信息）

### 4.4 节点的容错与降级

#### 容错机制

| 故障场景 | 检测方式 | 应对策略 |
| --- | --- | --- |
| 节点离线 | 心跳检测（1分钟无响应） | 标记离线，任务转其他节点或人工 |
| 节点超时 | 任务超时（5分钟无结果） | 返回部分结果，标记"数据缺失" |
| 节点错误 | 返回错误码或异常 | 重试1次，仍失败则转人工 |
| 数据不一致 | 多节点结果冲突 | 标记"需人工复核"，不自动裁决 |

#### 降级策略

示例：KimiClaw离线时的降级

正常流程：
  KimiClaw采集企业信息 → ArkClaw分析财务数据 → Hermes汇总
降级流程（KimiClaw离线）：
  Hermes检测到KimiClaw离线
  → 启用备用数据源（Hermes直接调用天眼查API）
  → 标记"数据采集节点离线，使用备用源"
  → ArkClaw继续分析（基于备用数据）
  → Hermes汇总（附带降级说明）

### 4.5 节点的扩展与收缩

#### 水平扩展

当某个节点的负载过高时，可以启动"副本节点"分担任务。

示例：KimiClaw负载过高
  → 启动KimiClaw-2（相同配置）
  → Hermes将新任务分配给KimiClaw-2
  → 两个KimiClaw并行工作
  → 负载均衡后，关闭KimiClaw-2

#### 垂直扩展

当某个节点的能力不足时，可以升级硬件或模型。

示例：ArkClaw报告生成太慢
  → 升级云端服务器配置（更多CPU/内存）
  → 或切换至更强的模型（云端大模型A → doubao-pro）
  → 性能提升后，恢复正常配置

### 4.6 Skill资产盘点：139个Skill的能力地图

节点设计完成之后，紧接着要回答一个现实问题：每个节点上到底跑了多少Skill？这些Skill覆盖了哪些业务场景？有无重复建设？有无能力盲区？

2026年6月，我对GitHub仓库yuzhaopeng-up/openclaw-workspace的skills/目录做了全量盘点，结果如下。

#### 4.6.1 总体规模与分布

skills/目录下共有139个子目录，每个子目录代表一个已注册的Skill。按业务领域分为六大类：

| 类别 | 数量 | 典型Skill | 定位 |
| --- | --- | --- | --- |
| 金融风控类 | 约30个 | 反欺诈、信用评估、AML、合规检查、交易异常检测 | 风险识别与拦截 |
| 金融业务类 | 约35个 | 信贷审批、贷款催收、精准营销、财富管理、保险核保 | 业务流程自动化 |
| 数据分析类 | 约20个 | 财务报表分析、尽职调查、企业估值、行业对标 | 数据采集与洞察 |
| 基础设施类 | 约10个 | ClawLink CLI、Redis消息总线、飞书Bot、GitHub异步 | 集群通信与运维 |
| 通用工具类 | 约25个 | 文档生成、报告输出、网络搜索、OCR识别 | 跨场景通用能力 |
| 其他 | 约19个 | 实验性Skill、原型验证、已退役的旧版本 | 探索与迭代 |

这个分布揭示了一个关键特征：金融业务类+金融风控类合计65个，占总量的47%，说明集群的核心资产集中在金融垂直场景。如果加上数据分析类的20个，金融相关的Skill达到85个，占比61%。这是龙马集群与通用AI助手的核心区别——不是什么都能做的"万金油"，而是深耕金融行业的"专家集群"。

#### 4.6.2 两种引擎架构

139个Skill中，约80个采用Full Engine Pattern，约30个为纯提示词型，其余29个处于混合或过渡状态。

Full Engine Pattern的典型结构：

skill-name/
  ├── SKILL.md          # 提示词主干（角色定义、工作流、约束）
  ├── _meta.json        # 元数据（版本、作者、依赖、权限）
  ├── engine.py         # Python执行引擎（API调用、数据处理、状态管理）
  ├── config.yaml       # 参数配置（API端点、超时、阈值）
  └── tests/            # 单元测试

纯提示词型的典型结构：

skill-name/
  ├── SKILL.md          # 完整的提示词（含工作流、示例、约束）
  └── _meta.json        # 元数据

Full Engine Pattern的优势在于可以调用外部API、操作数据库、执行复杂逻辑。典型例子是due-diligence（贷前尽调）——它的engine.py需要调用天眼查API采集企业工商信息，提取年报PDF中的财务数据，连接MySQL写入结构化结果，最后调用大模型生成分析报告。纯提示词型则更适合"输入文本→输出文本"的场景，比如report-generator——拿到结构化数据后，按模板写一份日报或周报，不需要额外引擎。

关键的数据点：最大的单个Python文件，scenario_registry.py达到117KB，data_handler.py达到142KB。这两个文件都在金融风控类Skill中——scenario_registry.py管理着数百个风险评估场景的规则注册与匹配，data_handler.py处理多源异构数据的解析、清洗和标准化。这种体量已经不是"脚本"级别，而是"工程模块"级别，说明成熟的Skill已经进入了工业级代码的范畴。

#### 4.6.3 重点Skill解剖

**金融智能体（financial_intelligence）**

这是整个集群中功能最密集的Skill，拥有10个子引擎：

1. DuPont分析引擎——自动拆解ROE为净利率、资产周转率、权益乘数三层，支持5年趋势对比和同业排名
2. 保证金计算引擎——根据交易所规则和合约规格，实时计算期货保证金需求
3. 风险扫描引擎——整合反欺诈规则库、AML黑名单、制裁名单，多维度风险信号扫描
4. 信用评估引擎——基于财务指标和非财务指标，生成信用评分卡
5. 流动性分析引擎——计算流动性覆盖率（LCR）、净稳定资金比率（NSFR）
6. 利率敏感性引擎——分析利率变动对资产负债表的影响，支持缺口分析和久期分析
7. 资本充足率引擎——按监管标准计算核心一级资本充足率、一级资本充足率、资本充足率
8. 关联方识别引擎——穿透股权结构，识别隐性关联方和一致行动人
9. 行业对标引擎——按申万行业分类，自动匹配同业上市公司，生成对标分析
10. 合规检查引擎——对照监管要求，检查财报数据的合规性，标注异常项

10个子引擎协同工作的方式是：主引擎接收任务后，根据任务类型激活1-3个子引擎并行执行，子引擎的结果汇总到主引擎，由主引擎做一致性校验后输出。以一次完整的杜邦分析为例——主引擎同时激活DuPont分析引擎（计算ROE拆解）、行业对标引擎（选取同业数据）、风险扫描引擎（检查是否有财务造假信号），三个子引擎并行执行，主引擎汇总后输出一份包含ROE拆解、同业排名、风险提示的综合报告。

**贷前尽调智能体（due-diligence）**

截至2026年6月，due-diligence已产出约115个上市公司的JSON+MD配对报告。每份报告包含：

- JSON文件：结构化数据卡，涵盖企业基本信息、财务指标、风险信号、信用评分等40+字段
- MD文件：Markdown格式的尽调报告，包含执行摘要、财务分析、风险扫描、行业对标、授信建议五个标准章节

115这个数字的背后是一个工程细节：起初due-diligence对每家企业只能输出MD格式，后续为了支持结构化查询和批量比对，增加了JSON输出通道。JSON+MD的配对设计，让同一份数据既能被人阅读（MD），又能被程序处理（JSON），体现了"数据一次生产，多端消费"的工程原则。

#### 4.6.4 能力地图的启示

盘点139个Skill之后，有三点发现值得记录：

第一，金融风控类和金融业务类的边界正在模糊。早期的设计中，"反欺诈"属于风控类，"信贷审批"属于业务类。但随着监管趋严，信贷审批流程中内嵌了反欺诈检查、AML筛查、合规审查，一个业务Skill实际上拉动了3-4个风控Skill。未来的趋势是"AIOps化"——业务Skill自动编排风控Skill，而非人工串联。

第二，基础设施类和通用工具类的Skill数量虽少（35个），但被依赖的频率最高。ClawLink CLI被约60个Skill间接依赖，Redis消息总线被4个集群协作Skill依赖。这符合基础设施的固有特征——数量少，但不可替代。

第三，约19个"其他类"Skill中，有7个是已退役的旧版本，6个是实验性原型，6个是等待合并的功能分支。退役Skill没有删除，而是保留在仓库中作为历史参考。这个实践来自一次教训——曾因为过早删除了一个"规则引擎v1"Skill，导致v2版本上线出Bug后无法回退到v1，只能从头重写。从那以后，退役Skill保留但标记status=deprecated，新生效的Skill标记status=active。

### 4.7 节点间的协作关系图谱

6个节点之间的数据流和依赖关系，可以用一个文字化的有向图来描述。理解这个图谱，是理解集群行为的关键。

#### 4.7.1 节点间的数据流向

核心数据流有7条主路径：

**路径1：Hermes → ArkClaw（调度指令）**
Hermes将任务拆解后，向ArkClaw发送分析指令。指令包含：任务目标、context（上下文数据）、deadline、输出格式要求。典型的指令格式是一个JSON消息，通过ClawLink加密通道发送。

**路径2：KimiClaw → Hermes（采集数据）**
KimiClaw完成数据采集后，将结构化数据返回Hermes。数据格式为JSON，包含：source（数据来源）、timestamp（采集时间）、confidence（置信度）、payload（实际数据）。如果采集失败，返回error_report而非数据。

**路径3：Hermes → MyOpenClaw（敏感数据委托）**
当Hermes判断任务涉及P2/P3级敏感数据时，将原始数据交给MyOpenClaw处理。这是集群中唯一一条"主动降级"路径——数据不在高性能的KimiClaw上处理，而是在本地化的MyOpenClaw上完成，牺牲速度换取安全。

**路径4：ArkClaw → CodeBuddy（代码审查请求）**
ArkClaw在生成报告时，如果涉及Python代码片段（如数据处理脚本、可视化代码），会委托CodeBuddy做代码审查。CodeBuddy返回审查结果：通过/需修改/拒绝，附具体意见。

**路径5：WorkBuddy → Hermes（定时任务结果）**
WorkBuddy执行定时任务后，将结果推送给Hermes。但与路径2不同，定时任务的结果通常是运维性质的（日志备份完成、Token消耗统计、Skill版本同步），不需要Hermes做进一步调度。

**路径6：CodeBuddy → GitHub（代码推送）**
CodeBuddy完成代码开发后，直接推送到GitHub仓库。这条路径绕过了Hermes——代码操作有独立的权限控制和审计链，不需要经过调度节点中转。

**路径7：KimiClaw → ArkClaw（数据直传）**
在贷前尽调场景中，KimiClaw采集的原始数据在Hermes的授权下，可以直传给ArkClaw做深度分析，避免经过Hermes中转增加延迟。但这条路径有严格限制：只允许JSON格式的结构化数据，不允许传输任何P2/P3级敏感数据。

#### 4.7.2 依赖关系与耦合度

6个节点的依赖关系可以分为三个层次：

**强依赖（核心路径，不可断开）：**
- Hermes → 所有节点（调度指令）
- 所有节点 → Hermes（结果返回）
这两条是集群运行的命脉。Hermes是唯一的调度中枢，没有Hermes，集群就是6个孤岛。

**弱依赖（增强路径，可降级）：**
- KimiClaw → ArkClaw（数据直传，可降级为经Hermes中转）
- ArkClaw → CodeBuddy（代码审查，可降级为跳过审查）
- MyOpenClaw → Hermes（脱敏数据返回，可降级为本地暂存）
弱依赖路径断开时，集群仍可运行，但效率或质量会下降。

**无依赖（独立路径）：**
- WorkBuddy → GitHub（日志备份）
- CodeBuddy → GitHub（代码推送）
- WorkBuddy → 本地存储（定时任务）
这三条路径完全独立，即使集群其他部分全部停摆，仍可正常运行。

#### 4.7.3 协作关系的动态演化

节点间的协作关系不是一成不变的。随着新Skill的加入，数据流向和依赖关系也在演化。

一个典型的例子是cluster-health-monitor（集群健康监控）Skill的加入。在v1版本中，节点健康状态由Hermes自行检测（心跳机制）。但Hermes调度任务和检测健康是相互矛盾的——当Hermes自身负载高时，心跳检测的实时性下降，可能出现"活节点被误判为离线"的情况。加入cluster-health-monitor后，健康检测改为独立执行，Hermes只需要读取监控结果。这个改动增加了一条新的数据流：cluster-health-monitor → Hermes（健康状态报告），同时降低了Hermes的自身负载。

另一个演化案例是feishu-group-bot（飞书群Bot协作）的加入。此前，集群与用户的交互只有Hermes→用户这一条单点路径。飞书Bot加入后，用户可以在飞书群中@特定的Bot节点直接下达任务，而不需要经过Hermes。这增加了一条新的控制路径：用户 → 飞书Bot → 节点。但为了保持Hermes作为调度中枢的地位，飞书Bot收到任务后，仍然会将任务注册到Hermes的任务队列，只是用户感知上更直接了。

这揭示了一个设计原则：新数据流可以增加，但"调度中枢唯一"的原则不可打破。无论通过哪条路径进来的任务，最终都要经过Hermes的统一调度。这不是技术限制，而是工程纪律——没有统一调度，集群就会退化为"各自为政的多节点"。

### 本章小结

本章我们详细介绍了龙马集群的节点设计与分工：

1. 设计原则：单一职责（每个节点只做一个领域，ArkClaw不碰代码，KimiClaw不写报告）、能力互补（节点之间不重叠，due-diligence三节点协同产出115份报告）、容错独立（KimiClaw宕机40分钟，集群仍15分钟输出快速评估报告）

5. 容错与降级：离线检测、超时处理、错误重试、数据不一致标记

6. 扩展与收缩：水平扩展（副本节点）、垂直扩展（硬件/模型升级）
