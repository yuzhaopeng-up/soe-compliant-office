## 二、系统概述

### 业务场景

一线巡检人员通过企业微信群发送巡检图文报告（含现场照片、位置、问题描述），管理人员需将分散的群消息结构化归档，形成可检索、可统计、可复盘的业务资产。

### 业务价值

| 维度 | 现状痛点 | 系统改善 |
|------|----------|----------|
| 数据散落 | 巡检信息碎片化在群聊中，无法检索 | 结构化归档到案例库，支持全文检索 |
| 隐私风险 | 客户名称/地址明文暴露 | 自动脱敏，区级以上遮盖 |
| 人工判断 | 故障是否需升级全凭经验 | 人工确认环节，系统提供升级建议 |
| 统计缺失 | 无巡检数据汇总 | 周报自动生成，统计表实时更新 |
| 归档断层 | 巡检做完即结束，无后续沉淀 | 自动沉淀到案例库，形成知识资产 |

### 核心流程（8-Phase）

```
P0 消息轮询 ──→ P1 图片下载 ──→ P2 字段提取 ──→ P3 隐私脱敏
                                                          │
P7 归档沉淀 ←── P6 周报生成 ←── P5 归档保存 ←── P4 人工确认
```

## 三、实践来源与设计依据

### Step1 实践：巡检群消息字段提取

原始消息：`@张工 早上好！今天去红谷滩区九龙湖基站巡检，同行人员：李明、王芳，发现空调外机异响，已拍照记录，预计2小时处理完毕。`

提取结果 → 归一化字段映射：

| 消息片段 | 提取字段 | 字段ID |
|----------|----------|--------|
| 张工 | 负责人 | person_in_charge |
| 李明、王芳 | 参与人员 | participants |
| 红谷滩区九龙湖基站 | 巡检地点 | location |
| 今天 | 巡检日期 | inspect_date |
| 空调外机异响 | 问题描述 | issue_desc |
| 已拍照记录 | 处理措施 | action_taken |
| 2小时 | 预计处理时长 | est_duration |

**关键经验**：群消息口语化程度高，需模糊匹配+上下文推理定位字段。缺省字段（如设备编号）需标记为null，不编造。

### Step2 实践：巡检记录归档沉淀

操作链：脱敏（红谷滩区→某区）→ 人工确认（是否升级故障工单 / 文件名 / 脱敏范围）→ 归档保存

**关键经验**：
1. 客户名称必须脱敏到区级，地标名（九龙湖）可保留
2. 人工确认至少3项：归档内容完整性 / 是否升级故障 / 脱敏范围
3. 文件名规范：`YYYYMMDD_负责人_参与人员_脱敏后地点`
4. 归档文档需含：元数据表 + 脱敏记录 + 原始消息（脱敏后）+ 人工确认记录

## 四、Phase 详细定义

### P0 消息轮询与过滤

**目的**：以5分钟为周期轮询企微群消息，通过白名单+关键词过滤，筛选出与巡检相关的图文消息。

**调用组件**：`scheduler`

**输入**：

```json
{
  "poll_interval": "5min",
  "group_whitelist": ["南昌巡检工作群", "九江装维调度群"],
  "keyword_filter": ["巡检", "基站", "机房", "光交", "设备", "故障", "异响", "断线", "停电", "抢修"],
  "data_source": {
    "type": "api_bridge | file_bridge | manual_import",
    "api_endpoint": "https://wxwork-api-bridge/v1/messages",
    "file_path": "./data/wx_messages.json",
    "auth": "env:WXWORK_API_TOKEN"
  }
}
```

**输出**：

```json
{
  "session_id": "POLL-20260627-001",
  "poll_timestamp": "2026-06-27T09:15:00+08:00",
  "raw_messages": [
    {
      "msg_id": "wxmsg_abc123",
      "sender": "张工",
      "timestamp": "2026-06-27T09:12:00+08:00",
      "content": "@张工 早上好！今天去红谷滩区九龙湖基站巡检...",
      "image_urls": ["https://wxwork.xxx/image1.jpg", "https://wxwork.xxx/image2.jpg"],
      "group_name": "南昌巡检工作群"
    }
  ],
  "filter_stats": {
    "total_fetched": 50,
    "whitelist_pass": 12,
    "keyword_hit": 3,
    "final_passed": 3
  }
}
```

**过滤规则**：

```
通过条件 = 群名∈白名单 AND (内容含任一关键词 OR 消息含图片)
```

**异常处理**：

| 异常 | 处理方式 |
|------|----------|
| API桥接不可用 | 降级为文件桥接模式（读取本地JSON文件） |
| 文件桥接也不可用 | 降级为手动导入模式（用户粘贴消息内容） |
| 轮询超时（>30s） | 跳过本轮，记录日志，下一轮继续 |
| 无新消息 | 输出空数组，不触发后续Phase |

**数据源降级优先级**：

```
API桥接（全量自动）→ 文件桥接（半自动导出）→ 手动导入（用户粘贴）
```

### P1 图片下载与OCR关联

**目的**：下载消息中的图片，通过视觉模型提取图片中的文字信息（设备编号、告警面板等），关联到对应巡检记录。

**调用组件**：`image_understanding` + `powershell`

**输入**：P0输出的 `raw_messages`

**处理逻辑**：

```
对每条消息的每张图片：
1. 下载图片到 .temp/images/{msg_id}_{seq}.jpg
2. 调用 image_understanding 提取图片信息
   - prompt: "识别图片中的设备编号、告警信息、仪表读数、位置标识等关键信息"
3. 将OCR结果合并到消息记录的 ocr_fields 中
```

**输出**：

```json
{
  "session_id": "POLL-20260627-001",
  "enriched_messages": [
    {
      "msg_id": "wxmsg_abc123",
      "sender": "张工",
      "content": "@张工 早上好！今天去红谷滩区九龙湖基站巡检...",
      "image_files": [".temp/images/wxmsg_abc123_1.jpg", ".temp/images/wxmsg_abc123_2.jpg"],
      "ocr_fields": {
        "device_id": "KT-SN-2024-0815",
        "alarm_info": "外机运行异响，压缩机振动偏大",
        "meter_reading": null
      },
      "group_name": "南昌巡检工作群",
      "timestamp": "2026-06-27T09:12:00+08:00"
    }
  ],
  "download_stats": { "total_images": 2, "downloaded": 2, "failed": 0 }
}
```

**异常处理**：

| 异常 | 处理方式 |
|------|----------|
| 图片URL过期/失效 | 记录failed_url，该图片标记为missing，其余图片继续 |
| 图片>5MB | 自动压缩后重试，压缩失败则跳过 |
| OCR识别结果为空 | ocr_fields置为null，不影响后续文字提取 |
| 图片下载超时 | 单张10s超时，超时跳过，记录日志 |

### P2 关键字段提取

**目的**：从消息文本和OCR结果中提取巡检关键字段，输出结构化记录。

**调用组件**：`info-extractor`

**输入**：P1输出的 `enriched_messages`

**提取字段定义**：

| 字段ID | 字段名 | 必填 | 提取来源 | 示例 |
|--------|--------|------|----------|------|
| record_id | 记录编号 | 自动 | 系统生成 | REC-20260627-001 |
| person_in_charge | 负责人 | 是 | @提及/发送者 | 张工 |
| participants | 参与人员 | 是 | "同行人员"/"陪同"/"配合"等关键词后 | 李明、王芳 |
| location | 巡检地点 | 是 | "去XX巡检"/"XX基站"等模式 | 红谷滩区九龙湖基站 |
| inspect_date | 巡检日期 | 是 | "今天"/"明天"/日期格式 | 2026-06-27 |
| device_id | 设备编号 | 否 | OCR提取 / 文本中"BTS-"/"KT-"等前缀 | KT-SN-2024-0815 |
| issue_desc | 问题描述 | 否 | "发现"/"存在"/"出现"等关键词后 | 空调外机异响 |
| action_taken | 处理措施 | 否 | "已"/"正在"等完成时态后 | 已拍照记录 |
| est_duration | 预计时长 | 否 | "预计X小时"/"约X分钟" | 2小时 |

| image_count | 图片数量 | 自动 | 关联图片文件数量 | 2 |

| 关键词 | 严重程度 |
|--------|----------|
| 断线/停电/瘫痪/无法/中断 | 高 |
| 异响/异常/告警/抖动/发热 | 中 |
| 正常/无异常/良好/巡检完成 | 低 |

### P3 隐私脱敏

**目的**：对客户名称、详细地址等敏感信息做脱敏处理，确保归档内容符合隐私保护要求。

**调用组件**：`archive-manager`（脱敏检查模块）

**输入**：P2输出的 `extracted_records`

**脱敏规则**：

| 数据类型 | 匹配规则 | 遮盖方式 | 示例 |
|----------|----------|----------|------|
| 客户名称（企业） | XX公司/XX集团/XX银行 | 替换为"某企业" | 江西银行→某企业 |
| 客户名称（个人） | 姓+名（2-4字中文，上下文判定） | 替换为"某X" | 王建国→某王 |
| 详细地址 | 省市后接门牌号/楼层 | 仅保留到区/县 | 红谷滩区九龙湖→某区 |
| 手机号 | 1[3-9]\d{9} | 保留前3后2，中间*** | 13812345678→138***78 |
| 证件号 | \d{17}[\dXx] | 保留前3后1，中间**** | 360***X |

**地名脱敏分级**：

| 级别 | 保留范围 | 适用场景 |
|------|----------|----------|
| L1 省 | 仅保留省份 | 跨省项目汇报 |
| L2 市 | 保留到地市 | 省级汇总报告 |
| L3 区 | 保留到区县（默认） | 部门内巡检归档 |
| L4 街道 | 保留到街道 | 内部故障排查 |

### P4 人工确认

**目的**：对归档内容、脱敏范围、是否升级故障工单进行人工确认，确保归档数据准确合规。

**调用组件**：`human-in-loop`

**输入**：P3输出的 `desensitized_records`

**确认项清单**：

| 序号 | 确认项 | 必选 | 风险等级 | 默认值 |
|------|--------|------|----------|--------|
| C1 | 归档内容完整性（字段是否准确） | 是 | L2 | 确认 |
| C2 | 脱敏范围是否合适 | 是 | L3 | 确认 |
| C3 | 是否升级为故障工单 | 是 | L3 | 不升级 |
| C4 | 图片是否含敏感信息需额外处理 | 否 | L2 | 否 |
| C5 | 归档文件名是否OK | 否 | L1 | 自动生成 |

**升级判定规则**（供人工参考）：

| 条件 | 建议操作 |
|------|----------|
| severity=高 且 action_taken仅"拍照记录" | 建议升级为故障工单 |
| severity=中 且 est_duration>4小时 | 建议升级为故障工单 |
| 同一位置30天内重复出现2次以上同类问题 | 建议升级并标注"重复故障" |
| severity=低 且 无问题 | 保持巡检记录 |

### P5 归档保存

**目的**：将确认后的记录保存为归档文档（.docx），图片按规范命名归档，同时更新统计表。

**调用组件**：`docx` + `xlsx` + `powershell`

**输入**：P4输出的 `confirmed_records`

**处理逻辑**：

#### 5a. 归档文档生成（docx）

每条记录生成一个归档Word文档，内容包含：

```
1. 标题：巡检归档记录 - {脱敏后地点}
2. 元数据表格（14行2列：归档编号/类型/目标/负责人/参与人员/地点/日期/设备编号/问题/措施/时长/状态/标签/隐私等级）
3. 脱敏信息说明
4. 原始消息（脱敏后）- 黄色底色引用块
```

### P6 周报生成

**目的**：每周五自动汇总本周巡检归档数据，生成结构化周报。

**调用组件**：`report-generator` + `xlsx` + `scheduler`

**触发方式**：`scheduler` 定时任务，cron表达式 `0 17 * * 5`（每周五17:00）

**输入**：`巡检统计表.xlsx` 中本周（周一至周五）数据

**周报结构**：

```
1. 执行摘要（1页内）
   - 本周巡检总数 / 涉及基站数 / 发现问题数 / 升级故障数
   - 关键发现TOP3（按严重程度排序）

2. 数据表格
   2.1 逐日巡检统计表（日期/巡检数/问题数/升级数）
   2.2 人员巡检排行（负责人/巡检次数/发现问题数）
   2.3 问题类型分布（空调/电源/传输/其他）
   2.4 严重程度分布（高/中/低占比）
   2.5 区域巡检覆盖（区名/巡检次数/问题数）

3. 行动建议
   - 紧急：严重程度=高且未解决的问题
   - 短期：重复出现2次以上的同类问题
   - 中期：巡检覆盖率偏低的区域
```

**输出**：

```json
{
  "report_type": "weekly",
  "report_period": "2026-06-22 ~ 2026-06-26",
  "report_path": "巡检案例库/2026-06/巡检周报_2026W26.docx",
  "summary": {
    "total_inspections": 23,
    "sites_covered": 15,
    "issues_found": 8,
    "escalations": 2,
    "top_issues": ["空调外机异响(3次)", "电源模块告警(2次)", "光衰超标(1次)"]
  }
}
```

**异常处理**：

| 异常 | 处理方式 |
|------|----------|
| 本周无巡检数据 | 生成"零巡检"周报，标注"本周无归档记录" |
| 统计表损坏/缺失 | 基于归档文档目录重建统计表后生成 |
| 周报生成失败 | 降级为纯文本周报，通过消息发送 |

## 六、安全铁律

| R5 | 归档操作记录审计日志 | 每次归档记录：操作人/时间/目标位置/内容摘要（前50字）/归档编号 |

## 七、容错与降级机制

| 故障点 | 主方案 | 降级方案 | 底线方案 |
|--------|--------|----------|----------|
| P0 企微API不可用 | API桥接拉取 | 文件桥接（本地JSON） | 手动粘贴消息 |
| P1 图片下载失败 | 重试1次 | 跳过该图片，记录missing | 归档记录标注"图片缺失" |
| P2 字段提取不完整 | info-extractor自动推断 | 标记missing_fields | P4人工补充 |
| P3 无法判断敏感级别 | 保守脱敏 | L3默认 | P4人工调整 |
| P4 人工确认超时 | 等待30分钟 | 按默认值自动确认 | 标记"待复核" |
| P5 docx生成失败 | 重试1次 | 降级为Markdown格式 | 纯文本保存 |
| P6 周报生成失败 | 重建统计表后重试 | 降级为纯文本周报 | 推送"本周数据异常，需人工生成" |
| P7 沉淀目标不可用 | 异步重试3次 | 暂存本地pending目录 | 下次轮询时重试 |

### 熔断规则

| 触发条件 | 熔断动作 |
|----------|----------|
| 连续3次轮询返回0条消息 | 暂停轮询，告警通知，检查API状态 |
| 单次提取置信度全部<0.5 | 跳过本轮归档，转入人工复核队列 |
| 归档失败率>30%（连续5轮） | 暂停自动归档，全面人工检查 |
| 单日归档量>100条 | 触发流量控制，分批处理 |
