# Skill: 云计算商机情报系统 (Cloud Opportunity Radar)

## 核心理念

**不是单次评分，而是情报闭环——普通Skill做一次评估出个分，高级Skill把"采集→验证→评分→分层→确认→出报→归档"串成7x24可运转的情报生产线，让商机从信息海洋中自动浮现，而非等人来查。**

## 编排架构

本 Skill 采用 **7 Phase 强制组件编排**，通过 `phase-orchestrator` 技能驱动 7 个独立 sub-Agent 顺序执行。每个 Phase 由独立 Agent 执行，Phase 间通过结构化 JSON 传递数据。禁止跳过任何 Phase，禁止用自由文本替代组件输出。

```
┌─ Orchestrator Agent ──────────────────────────────────────────────────────────────┐
│  Phase 1 → web-search       : 搜索采集（地域词×能力词组合矩阵，多源并发采集）       │
│  Phase 2 → info-extractor   : 信源白名单验证（S/A/B分级，低信源过滤）               │
│  Phase 3 → data-analyst     : 双模型评分（信息质量模型 + 业务价值模型 → J1-J5）      │
│  Phase 4 → data-analyst     : P0/P1/P2分层（结合J分级+时效性+战略权重）             │
│  Phase 5 → human-in-loop    : 高价值线索人工确认（P0线索强制审批）                   │
│  Phase 6 → report-generator : 生成商机雷达日报（执行摘要+数据表格+行动建议）         │
│  Phase 7 → archive-manager  : 归档沉淀（去重+标签+脱敏+入库）                       │
└───────────────────────────────────────────────────────────────────────────────────┘
```

**执行方式**：加载 `skill` 工具，参数 `name: "phase-orchestrator"`，按其 SKILL.md 中的通用调度流程执行。本 Skill 负责提供 7 个 Phase 的完整 prompt 模板，当前 Agent 在调度前读取模板、替换占位符、构造 pipeline_config 传给 orchestrator。

**降级模式**：若 task 工具不可用或 phase-orchestrator 加载失败，退回单 Agent 模式：由当前 Agent 按 Phase 定义的处理规则手动执行全部 Phase，标注 `[降级模式：多Agent编排不可用]`。

## 输入参数

### 必须参数

| 参数 | 类型 | 说明 |
|------|------|------|
| `region` | 字符串 | 目标地域，如 `"江西"`、`"广东"` |
| `industry` | 字符串 | 目标行业，如 `"教育"`、`"医疗"`、`"政务"`，默认 `"全行业"` |

### 可选参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `keyword_matrix_override` | JSON对象 | `null` | 自定义搜索词矩阵，覆盖默认矩阵 |
| `source_whitelist_override` | JSON对象 | `null` | 自定义信源白名单，覆盖默认白名单 |
| `scoring_weights` | JSON对象 | `null` | 自定义评分权重，如 `{"产品匹配度":0.30}` |
| `p0_threshold` | 枚举 | `"J2"` | 触发人工确认的最低J等级，`"J1"`/`"J2"`/`"J3"` |
| `time_range` | 枚举 | `"month"` | 搜索时间范围，`"week"`/`"month"`/`"quarter"` |
| `output_format` | 枚举 | `"docx"` | 日报输出格式，`"docx"`/`"markdown"`/`"html"` |
| `dry_run` | 布尔 | `false` | 试运行模式：只执行Phase1-4，跳过人工确认/日报/归档 |

### A级（行业权威源，置信度 0.65-0.84）

| 来源 | 域名/平台 | 说明 |
|------|----------|------|
| 天翼云官网 | ctyun.cn | 产品方案和标杆案例 |

| 千里马招标网 | qianlima.com | 行业标讯平台 |

### B级（参考补充源，置信度 0.40-0.64）

| 来源 | 域名/平台 | 说明 |
|------|----------|------|
| 知乎专栏 | zhihu.com | 行业分析，需交叉验证 |

| 行业自媒体 | 各类 | 仅供参考，不作为独立信源 |

### 过滤规则

- B级来源的情报不得作为J1-J2判定的唯一依据

- 同一情报若仅有B级来源，J等级上限锁定为J3

## Phase 1 — 搜索采集

**调用组件**：`web-search`

**输入契约**：

```json
{
  "region": "江西",
  "industry": "教育",
  "time_range": "month",
  "keyword_matrix_override": null,
  "search_queries": [
    "江西 教育局 智慧校园 云平台 采购",
    "江西 5G专网 天翼云 招标",
    "..."
  ]
}
```

**处理规则**：

1. 根据地域词 × 能力词矩阵，生成 10-20 条搜索 Query
2. 每条 Query 调用 online_search 执行搜索，参数：`search_recency_filter` 按 `time_range` 映射
3. 对每条搜索结果，提取：标题、摘要、链接、来源域名、发布日期
4. 去重：按标题 + 来源域名去重，保留最新版本
5. 对采购意向/招标类结果，尝试 webfetch 获取正文详情

**输出契约**：

```json
{
  "phase": "search_collection",

    "region": "江西",
    "industry": "教育",
    "time_range": "month",
```

## Phase 2 — 信源白名单验证

**调用组件**：`info-extractor`

**输入契约**：Phase 1 的 `raw_intelligence` 数组 + 信源白名单配置

**处理规则**：

1. 遍历 `raw_intelligence`，对每条情报的 `source_domain` 与白名单匹配
2. 匹配结果赋予信源等级（S/A/B/非白名单）和对应置信度区间
3. 调用 info-extractor 从正文提取结构化字段：
   - 客户名称、项目名称、预算金额、采购方式、招标截止日、技术要求、联系方式
4. 标注缺失字段
5. 过滤：非白名单信源且无白名单来源交叉佐证 → 移入 `low_confidence` 分组，不进入后续评分

## Phase 3 — 双模型评分

**调用组件**：`data-analyst`

**输入契约**：Phase 2 的 `validated_intelligence` 数组

**处理规则**：

对每条情报，分别用两个模型打分：

### 模型A — 信息质量评分（满分100）

| 维度 | 满分 | 评分标准 |
|------|------|---------|
| A1.信息完整度 | 25 | 关键要素命中数/8（客户/项目/预算/时间/技术/采购方式/决策人/评标标准），每项3.1分 |
| A2.信息时效性 | 25 | 已截标=5，招标中=15，意向公示=20，方案征集=22，早期规划=25 |
| A3.信息可信度 | 25 | S级信源=23，A级=18，B级=13，非白名单=5；多源交叉+3 |
| A4.需求明确度 | 25 | 技术要求具体=22，方向明确=16，模糊提及=10，仅品类=5 |

### 模型B — 业务价值评分（满分100）

| 维度 | 满分 | 评分标准 |
|------|------|---------|
| B1.项目规模 | 20 | ≥500万=18，200-500万=14，50-200万=10，<50万=4，未公示=8 |
| B2.产品匹配度 | 25 | 完美匹配(写明5G+天翼云)=25，高匹配=20，一般=12，低匹配=6，无匹配=2 |
| B3.战略价值 | 20 | 行业标杆+可复制=18，标杆但不可复制=14，一般项目=8，边缘=4 |
| B4.竞争优势 | 20 | 需求独占指向=18，强优势=14，均势=8，劣势=3 |
| B5.转化可行性 | 15 | 高(有决策人+无竞品)=13，中=9，低(信息盲区大)=5 |

### J1-J5分级标准

| 等级 | 名称 | 判定条件 | 含义 |
|------|------|---------|------|
| **J1** | 确定商机 | 信息质量≥80 且 业务价值≥85 | 确定性高价值，立即行动 |
| **J2** | 优先商机 | 信息质量≥70 且 业务价值≥75 | 高价值重点跟进 |
| **J3** | 培育商机 | 信息质量≥55 且 业务价值≥55 | 有价值需培育 |
| **J4** | 观察商机 | 信息质量≥40 或 业务价值≥40 | 价值有限，观察为主 |
| **J5** | 暂缓商机 | 信息质量<40 且 业务价值<40 | 低价值，暂缓 |

**特殊规则**：

- 纯B级信源的情报，J等级上限为 J3
- 非白名单信源的情报，J等级上限为 J4
- 需求明确写"天翼云"或"5G专网"的，B2产品匹配度固定25分，B4竞争优势固定18分
- 预算未公示的项目，B1项目规模默认8分（中等偏下）

**输出契约**：

```json
{
  "phase": "dual_scoring",
  "scored_intelligence": [
    {
      "intel_id": "I-001",
      "project_name": "宜黄县职业教育中心智慧校园项目",
      "info_quality": {
        "A1_completeness": 18.8,
        "A2_timeliness": 15,
        "A3_credibility": 23,
        "A4_clarity": 16,
        "total": 72.8
      },
      "business_value": {
        "B1_scale": 10,
        "B2_match": 20,
        "B3_strategy": 14,
        "B4_advantage": 14,
        "B5_feasibility": 9,
        "total": 67
      },
      "j_grade": "J3",
      "j_grade_cap": null,
      "scoring_notes": "预算未公示拉低B1；B级信源上限J3不触发"
    }
  ]
}
```

**降级策略**：若 data-analyst 加载失败，由当前 Agent 按上述评分标准手动计算，标注 `[降级模式：data-analyst未加载]`。

## Phase 4 — P0/P1/P2 分层

**调用组件**：`data-analyst`

**输入契约**：Phase 3 的 `scored_intelligence` 数组

**处理规则**：

基于 J 等级 + 时效性加权 + 战略修正因子，计算综合优先级得分，映射到 P0/P1/P2：

### 综合优先级公式

```
综合优先级 = J等级分(40%) + 时效性分(30%) + 战略修正(30%)

J等级分：J1=100, J2=80, J3=60, J4=40, J5=20
时效性分：截标倒计时≤7天=100, ≤30天=80, ≤90天=60, >90天=30, 无明确时间=20
战略修正：5G+云融合需求=100, 标杆客户=90, 政策驱动=80, 一般项目=60, 边缘=30
```

### P分层映射

| 优先级 | 条件 | 含义 | 处置原则 |
|--------|------|------|---------|
| **P0** | 综合优先级≥80 | 核心商机 | 强制人工确认 → 24小时内响应 |
| **P1** | 综合优先级60-79 | 重要商机 | 重点跟进 → 3天内响应 |
| **P2** | 综合优先级<60 | 一般商机 | 纳入监控 → 常规跟进 |

**输出契约**：

```json
{
  "phase": "priority_layering",
  "layered_intelligence": {
    "P0": [
      {
        "intel_id": "I-001",
        "project_name": "...",
        "j_grade": "J2",
        "priority_score": 85,
        "priority_breakdown": {
          "j_score_component": 32,
          "timeliness_component": 24,
          "strategy_component": 29
        },
        "urgency_note": "招标截止7月15日，剩余20天"
      }
    ],
    "P1": [...],
    "P2": [...]
  },
  "summary": {
    "P0_count": 3,
    "P1_count": 8,
    "P2_count": 16,
    "total_valid": 27
  }
}
```

**降级策略**：若 data-analyst 加载失败，由当前 Agent 按公式手动计算，标注 `[降级模式]`。

## Phase 5 — 高价值线索人工确认

**调用组件**：`human-in-loop`

**输入契约**：Phase 4 的 `P0` 数组（+ 用户配置的 `p0_threshold` 决定是否包含 P1 顶部线索）

**处理规则**：

1. 仅对 P0 线索启动人工确认流程（`p0_threshold` 设为 "J2" 时，额外包含 J2+P1 线索）
2. 生成审批单，包含：
   - 线索摘要（项目名/客户/预算/J等级/P等级）
   - 核心判断依据（信源等级/产品匹配度/竞争优势）
   - 需人工确认的关键问题：
     - 该客户是否有本地客户经理对接？
     - 是否已有友商接触信息？
     - 预算金额是否与内部掌握一致？
3. 等待人工确认后，更新线索的确认状态和补充信息
4. 根据确认结果调整 J 等级和 P 优先级

**输出契约**：

```json
{
  "phase": "human_confirmation",
  "confirmed_leads": [
    {
      "intel_id": "I-001",
      "confirmation_status": "confirmed",
      "confirmed_by": "张经理",
      "confirmation_time": "2026-06-26T14:30:00",
      "supplementary_info": {
        "local_account_manager": "李工",
        "competitor_status": "移动已接触",
        "budget_verified": true,
        "j_grade_adjusted": "J2",
        "p_priority_adjusted": "P0"
      }
    }
  ],
  "pending_leads": [
    {
      "intel_id": "I-003",
      "confirmation_status": "pending",
      "reason": "客户经理请假，下周确认"
    }
  ],
  "rejected_leads": [
    {
      "intel_id": "I-007",
      "confirmation_status": "rejected",
      "reason": "该项目已由友商签约"
    }
  ]
```
